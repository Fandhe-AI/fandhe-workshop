# コメント規約

## 目的

後続の読み手（Claude を含む）は、渡された情報からしか判断できない。
コメントには、リポジトリ全体から見たそのファイルの役割と、他ファイル・他サービスとの文脈を埋め込み、
ファイル単体で文脈が伝わる状態にする。

## 何を書くか

- このファイル・関数・ジョブの役割と責務境界（冒頭に 1〜2 行の要約）
- 呼び出し元・呼び出し先の文脈（「〜から呼ばれる」「〜を呼んで〜を返す」）
- 他ファイル・他サービスとの契約（引数・終了コード・前提条件・連動して更新する箇所）
- 非自明な前提・副作用・エラー処理の意図（なぜその書き方にしたか）
- 判断の根拠になった計測値・決定には日付（`YYYY-MM-DD`）を添える

## 何を書かないか

- コードを読めば分かる逐語説明（`i=$((i + 1))  # i を 1 増やす` 等）
- 陳腐化しやすい実装詳細の重複（コードと二重に管理しない）
- 変更の経緯（「〜を修正した」等）。経緯はコミットメッセージ・PR に書く
- 秘密情報・実在の認証情報の例

## 言語

コメントは日本語で書く（`.claude/rules/japanese-style.md`）。スクリプトが出力するエラー・usage は英語。

## ファイル種別ごとの形式

### シェルスクリプト（`scripts/**/*.sh`）

shebang の直後に、役割・呼び出し元・終了コード・回帰テストの場所を書く。

```bash
#!/usr/bin/env bash
# staged 差分に対する簡易シークレット検知（lefthook pre-commit から呼ばれる）。
#
# 終了コード: 0 = 検出なし / 1 = 検出（コミット拒否） / 2 = 検査を完了できない（fail-closed で拒否）。
# 回帰テストは scripts/hooks/test-hooks.sh（CI の test-hooks ジョブ）。
set -euo pipefail
```

関数には、引数と戻り値・呼び出し側が知るべき前提を 1〜3 行で書く（`# require_cmd <name>: ...` の形）。

### Makefile

- ターゲット行末の `## 説明` は `make help` の生成元。自由記述のコメントではないため、形式を崩さない
- 方針・互換性の注意は、ファイル冒頭の `#` コメントに書く

### YAML（`lefthook.yml`・`.github/workflows/**`）

- ファイル冒頭に、役割と、従うルール（`.claude/rules/git-hooks.md`・`github-actions.md`）を書く
- ジョブ・ステップには、存在理由と、変更時に連動して直す箇所を書く（例: `ci-complete` の `needs`）
- 固定した版・SHA には、版を示すコメントを付ける（`# v7.0.1`）

### Rust（導入後）

- クレート・モジュールの入口に `//!`、公開 API に `///` で 1〜2 行の役割要約を必ず付ける
- `unsafe`・`unwrap` / `expect`・`#[allow(...)]` には、安全である理由・許容する理由を書く

### TOML・JSON

- TOML は、既定から変えた設定に理由を書く（例: `Cargo.toml` の `[profile]`。`.claude/rules/rust-build-profile.md`）
- JSON はコメントを書けないため、説明は README か対応するルールに置く

## 既存のコメントを直すとき

コードを変えたら、同じ変更でコメントも直す。コメントだけを追加・補強する作業は `comment-code` スキルで行い、
コード自体は変更しない。
