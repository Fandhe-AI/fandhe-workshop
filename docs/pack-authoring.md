# 教材の作成者向けの文書

教材（パック）を作る人向けの文書です。仕様は private のため本文を転記せず、ID（VER-11・VER-12・VER-14・D-43・D-51・D-52）で参照します。

版と保存済みの履歴の節（TASK-180）に続けて、主版を上げる条件と `pack.vocab` の書き方の規約（TASK-179）を書いています。

公開の資料は、この文書のほかに 8 種類あります（TASK-411・TASK-412、AUTHOR-12）。欄の名前と型は `docs/schema-format-b.md`、語の一覧は `docs/vocabulary/README.md`（正は `docs/vocabulary/vocabulary.md`）、操作プロファイルと外観は `docs/operation-profile.md`、ビューは `docs/views.md`、書けないことと回避は `docs/known-gaps.md` です。あわせて、コマンドの使い方は `docs/cli-guide.md`、最小の教材パックの例は `docs/examples/`、診断コードの意味と早見表は `docs/diagnostics.md` にあります。

## 教材の版と保存済みの履歴

保存済みの履歴は、4 軸の版（エンジン・教材形式・教材内容・参照元）を記録します。教材内容の軸は、`pack.version` と
`content_hash` の組です。

`content_hash` は、IR から本文の木（`body_doc`・`body_levels_doc`）だけを除いて求めます（D-51）。求め方の実装は
`crates/contract/src/content_hash.rs` にあります。

## 本文だけの修正は `content_hash` を変えない

本文だけを直した教材は、`content_hash` が変わりません。保存済みの履歴から見ると同じ版のままで、受講中の画面の本文だけが
新しくなります。

本文以外の欄（例: 選択肢の `label`）を足すと IR が変わり、`content_hash` も変わります。

## 主版を上げ忘れた本文の修正は判定に現れない

主版を上げ忘れて本文だけを直すと、その修正は履歴の版の判定に現れません（VER-12）。エンジンは、本文の修正を履歴の版の違いとして
検出できません。

本文の版は `pack.version` で示す運用で補います（VER-11）。上げ忘れを警告する検査はありません（D-52）。主版を上げる判断の基準は、
次の「主版を上げる条件」に書きます。

## 主版を上げる条件（`pack.version`）

`pack.version` は `主.副.修` の十進表記（例: `1.0.0`）で書きます。先頭に 0 を付けたり成分の数を過不足にしたりすると、
エンジンが版の記録を作れません。`validate` は、この形を検査しません（2026-10-19 時点）。YAML では文字列として読まれます。

主版を上げるのは、流れが変わる変更をしたときです（VER-11・D-52）。基準は「既存の履歴の入力の列を新しい版で適用し直したとき、
同じ状態にならない変更」です。次は例で、網羅ではありません。

- Step の追加・削除
- Step の順序・`next`・分岐の条件の変更
- 開始点（`starts`）の変更
- 入力・確認・規則の変更のうち、同じ入力で進み方や世界状態が変わるもの

主版を上げる理由は 3 つです。

- 主版が違う履歴は、履歴の位置によらず表示だけになります（`content_major`。VER-6）
- 旧版の成果物を残すのは、主版を上げたときだけです（D-52）。旧版で続けられる経路が残ります。版つき URL の案は、最新版と同じ配信の
  先頭区間の下に旧版の配信物の写しを置く形（`/<配信の根>/v<主版>/`）です。残す範囲と担当は決まっていません（VER-9・VER-10。
  案と限界は `docs/testing.md` 5.379 と `docs/known-gaps.md`）
- 上げ忘れて副版のまま Step を足すと、足した Step より先へ進んだ履歴は表示だけ（`replay_diverged`）になり、旧版も残りません
  （VER-5・D-52）。旧版が残っていない履歴は、エンジンが別の版を探さないため表示だけのままです（`docs/testing.md` 5.381）。上げ忘れを警告する検査はありません（D-52）

流れが変わらない変更（文言・表示名・外観など、IR は変わっても適用し直した結果が変わらないもの）は、副版か修正版を上げます。
エンジンは副版と修正版を区別せず、どちらも適用し直して写しと一致すれば変換して開きます（VER-4）。使い分けは作成者に任せます
（決まりはありません）。

本文だけの修正は主版の判定に現れません（前の 2 節）。本文の版を示したいときは、副版か修正版を上げます（VER-12）。

## YAML の値の書き方（形式 B）

文字列の欄は、引用符なしで `true`・`no`・`1.10`・`010`・`null` と書いても、書いたとおりの文字列として読みます
（PACK-4）。`1.10` が `1.1` に、`010` が `10` や `8` に変わることはありません。

`do`・`body` のような省略できる欄に引用符なしの `null`・`~` を書くと、未設定ではなく、その字面の文字列になります。
未設定にしたいときは、欄そのものを書かないでください。

同じ表に同じキーを 2 回書くと `E-PARSE` で拒否します。引用符の有無だけが違うキー（`true:` と `'true':`）も同じキーです。
構文の誤りには、行と桁が付きます（複数文書の YAML は位置が付きません）。

数値の欄は 10 進で書いてください。`0x1f`・`0o17`・`0b11` のような 10 進でない整数は、どの欄でも `E-PARSE` で拒否します
（PACK-5。黙って 31 などに読み替えないためです）。形式 A（TOML）も同じです。形式 B で文字列として書きたいときは
`'0x1f'` のように引用符で囲んでください。診断には値を写さず、行と桁だけを示します。

形式 B では、アンカー（`&x`）・エイリアス（`*x`。マージキー `<<: *x` を含む）・タグ（`!t`・`!!str`・`!!int` など）・
複数文書（`---` で区切った 2 つ目以降の文書）も、どの欄でも `E-PARSE` で拒否します（PACK-5。YAML の処理系が黙って
展開・解決して、書いた内容と違う値になるのを避けるためです）。同じ値を何度も使いたいときはそのまま書くか、
モジュールを使ってください。文字列にしたいときは `!!str` ではなく引用符で囲んでください。1 つの文書の先頭の `---`
と末尾の `...` は書けます。形式 A（TOML）には、これらの記法がありません。

開始点（`starts`）は、全章を合わせて 1 件以上が必要です。0 件の教材パックは、`validate` の検査で `E-STRUCTURE` として
拒否します（PACK-25）。モジュールの `starts` は数えません。

`commands`・`views` など、語彙の型付けが入るまで自由な値として通す欄の中の引用符なしの値は、文字列にならず
YAML の型のままです。重複キーの拒否だけが及びます。

## 学習モジュールの呼び出し（`use`）

共通の流れを `modules/<名前>/module.yaml` に 1 か所だけ書き、章の Step から `use` で呼ぶと、呼んだ数だけ実体になります（PACK-19）。

```yaml
- id: r1-impl
  title: 1 周目の実装
  use:
    module: issue-to-merge   # モジュールの ID
    instance: round1         # 実体の名前（同じ呼び出し元の中で重複させない）
    args: { root: "42" }     # params の既定値に重ねる
```

- 実体の ID は `<モジュール ID>@<実体名>`、その Step の実体は `<モジュール ID>@<実体名>/<Step ID>` です。入れ子の実体は `<親の実体 ID>/<モジュール ID>@<実体名>` になります。
- モジュールの定義を 1 か所直すと、そのモジュールを使うすべての実体に反映されます。3 周目の実体は、章の定義ファイルを 1 つ足すだけで書けます（既存のファイルは変えません）。
- モジュールの文字列の `${名前}` は、コンパイル時に `args`（なければ `params` の既定値）で 1 回だけ置き換えます。差し込んだ値の中の `${` は、もう一度は置き換えません。`${` を字面のまま書く方法はありません。
- 置き換えない欄は、`id`・`body`・`body_levels`・`next[].to` と、連想配列のキーです。章（`main`）は引数を持たないので、`${` は字面のまま残ります。
- `args` の値は文字列で書きます。`root: 42` のような数値・真偽値は `E-PARSE` になるため、引用符で囲んでください。
- `module` と `instance` は `[A-Za-z0-9_.-]` の短い識別子にします（`@`・`/` は使えません）。
- `use` を持つ Step には `input` を書けません。同時に書くと `E-STRUCTURE` です（章の Step・モジュールの中の Step のどちらも）。
- モジュールの `starts` は、実体ごとに `<実体 ID>#<開始 ID>` として展開します。置き換えるのは `effects` と `requires` だけです。
- 開始点の `requires`（開始条件）と `unmet`（満たさないときの文面の ID）は、両方そろえて書きます。片方だけは `E-STRUCTURE` です。`requires: null` は省略と同じ扱いで、`unmet` だけが残ります。開始の前に、開始先の Step が属する実体の根で条件を評価します。満たすときだけ開始し、満たさない・評価できないときは開始せず `unmet` の文面を示します。状態は変わりません（TASK-51、PACK-18）
- 展開中の経路にあるモジュールを再び呼ぶ巡回（自分を呼ぶ場合を含む）は `E-MODULE-CYCLE` です。巡回を閉じる `use` の Step に `a → b → a` の形の経路つきで付きます。モジュール名が `${名前}` に由来する場合は、引数の値を出さないため経路は付きません。
- 入れ子は 8 段までです。9 段目の呼び出しは展開せず `E-MODULE-CYCLE` にします。これは巡回とは別の検査で、巡回しない深い入れ子にだけ効きます。未定義のモジュールは `E-REF-MODULE`、未定義の `${名前}` は `E-STRUCTURE` です。
- `use` に書けるのは `module`・`instance`・`args` だけです。実体ごとの案内レベルの `guidance` は語彙に無く、書くと `compile` も `validate` も `E-PARSE` です（D-55、PACK-45）。案内レベルは開始点で渡します
- `use` で呼ぶと、実体は必ずモジュールの先頭の Step から始まります。先頭の Step を省く語は無く、`use` に省く指定（`start` など）を書くと `compile` も `validate` も `E-PARSE` です（D-43、PACK-51）。実体ごとに後ろの Step を飛ばしたいときは、先頭の Step を振り分けの Step にして、`next` に `when: {param: {name: <引数>, eq: "<値>"}}` を書きます（例は `issue-to-merge` の `st-3-2` と `setup`）。飛ばした Step は IR に残り、遷移で通らないだけです（途中開始の「省略」とは別です）。
- ヒントは、`hints` の ID を `${名前}` で渡せば実体ごとに変えられます。ただし置換後の ID が定義されているかは検査しないので、未定義の ID を渡すとヒントが出ません。本文の Markdown とヒントの定義（文面・`levels`）は置換しません（`docs/known-gaps.md` の PACK-45）
- 本文は実体ごとに同じ木になり、本文の未定義の `${名前}` も検査されません。実体ごとに変えたい語は、引数で `do` に渡し、拒否・問い返しの文面の `{{step_do}}` で出します（TASK-302）
- 引数の型と範囲は、`params` の隣の `param_types` で宣言できます（語彙 1.7、PACK-51）。宣言した引数に型や範囲に合わない値を渡す（`"flase"` など）と、`compile` も `validate` も `E-STRUCTURE` で止めます。引数は文字列のままなので、書き間違いが `condition.param` の `eq` と一致せず、黙って別の分岐に倒れるのを防ぐためです。

    ```yaml
    params: {setup: "true", rounds: "2", mode: fast}
    param_types:
      setup: {type: bool}                 # "true" か "false" だけ
      rounds: {type: int, min: 1, max: 3} # 10 進の整数（"01"・"+1" は不可）。両端を含む
      mode: {type: enum, values: [fast, slow]}
    ```

    - 既定値（`params`）も同じ規則で検査します。呼ばれないモジュールの宣言も検査します
    - 宣言のない引数は、従来どおり検査しません。`pack.vocab` が 1.7 未満で `param_types` を使うと `E-VOCAB-MISMATCH` です
    - `condition.param` の `eq` に書く値が宣言に入るかは検査しません（`docs/known-gaps.md` の PACK-51）
    - 入れ子の呼び出しは、`${名前}` を置き換えた後の値で検査します。診断に値は含めません
- 呼ばれないモジュールは IR に出ません。
- モジュールの `input`・`confirm` が `${名前}` を含む場合は、置き換えた後の宣言を、入力方式・確認・操作プロファイル（`E-PROFILE-TEXT`・`E-PROFILE-NO-INPUT`）の規則で検査します。置き換える前の宣言は検査しないので、`kind: "${k}"` のように書けます。診断はモジュールの定義ファイルと Step で示し、引数の値は含めません。

## 実体どうしの世界状態の経路（引数で分ける・意図して共有する）

世界状態は教材全体で 1 つで、実体ごとに分かれていません。同じ経路に書く実体は上書きし合い、後に書いた方が残ります（`put`・`replace` は要素ごと置き換え、`set_attr` は属性を書き換えます）。経路の重なりは `validate` も `compile` も報告しません。意図した共有と誤りを、経路だけでは見分けられないためです（TASK-251 の決定。MOD-18）。

- 周回や実体ごとに別の成果物にしたい経路は、実体の引数で分けます。引数の値が実体どうしで重ならないように決めるのは作成者の責任です

    ```yaml
    - put: { path: "issues/root-${root}", attrs: { state: open } }
    ```

- 同じ題材に機能を足す流れ（同じ README を各実体が更新する）では、引数を使わない固定の経路で意図して共有してかまいません

    ```yaml
    - set_attr: { path: shared/README.md, attr: status, value: "${tag}" }
    ```

- チェックポイントへの復帰は、保存の後に持ち主（保存した時点の実体）が書いた経路だけを保存の時点の値へ戻します。共有の経路に持ち主と他の実体の両方が書いた場合は、他の実体の書き込みも含めて戻ります。他の実体だけが書いた経路は、共有の経路でも戻りません。共有するのは、この帰結を受け入れる場合に限ってください
- 誤った重なりは、2 周分の模範解答を教材テストの `playthroughs` に書き、各周回の成果物の経路が期待どおりに残ることで確かめます

## 入力方式（`input`）

Step の `input` は、`kind` で 5 方式と待機（`wait`）・実行環境の操作（`env_action`）から選びます（PACK-10・PACK-34）。ここに書けるのは次の欄だけで、未知の欄・
未知の `kind` は `E-PARSE`、意味の制約に反する宣言は `E-STRUCTURE` になります。

| `kind` | 欄 | 意味の制約 |
|---|---|---|
| `command` | `name`、`args`（各要素は `name`・`positional`・`required`・`shape`） | 名前は空でなく、引数名は重複しない。`shape` は `kebab_case`・`digits`・`any`（既定は `any`） |
| `text` | `min`・`max`（0 以上の整数。どちらも必須） | `min` は `max` 以下 |
| `choice` | `options`（各要素は `id`・`label`） | 1 件以上で、`id` は重複しない |
| `ui_action` | `targets`（各要素は `view`・`path`） | 1 件以上で、どれも空でない |
| `approval` | `revise`（省略可。語彙 1.5。「承認の『直す』の候補と表示名」の節） | `revise` 以外の欄を足すと `E-PARSE` |
| `wait`（EP-1） | なし | 欄を足すと `E-PARSE`。Step の `processing` が 1 件以上でないと `E-STRUCTURE` |
| `env_action` | `action`（必須。`save` か `export`。語彙 1.5。「保存・書き出しを入力とする Step」の節） | 未知の値・欄の欠け・未知の欄は `E-PARSE`。Step の `processing` を持つと `E-STRUCTURE` |

`text` が判定するのは、空でないことと文字数だけです。内容の良し悪しを判定する欄は書けません（`contains` や
`pattern` は `E-PARSE`）。受け付けた入力の分類は `free_text_unjudged`、範囲外は `bad_arg_shape` で拒否します。

- 文字数はコードポイントで数えます（絵文字は 1 文字）
- 前後の空白は数えません。空白だけの入力は空として常に拒否します（`min: 0` でも同じです）。この扱いは、spec が
  「空でないこと」としか書いていないことからの推定による決定です（2026-10-15）
- 下限・上限はどちらも含みます

`wait` は受講者の入力を要さず、`processing` の進行の完了で受付になります。`processing` が無い待機は先へ進めない
ため拒否します。この決定は、spec に明文がなく EP-1 の説明からの推定によります（2026-10-15。spec 側の確認が望ましい）。
`processing` があって `wait` でない Step（`command` との併用など）は書けます。`processing` の欄は「処理中の進行（`processing`）」の節を見てください。

取り消し（EP-2）は `input.kind` ではなく、規則の `on: { cancel: true }` で受けます。`kind: cancel` は未知の `kind` として
`E-PARSE` です。どの入力方式の Step にも書け、意味を持つのはその規則を書いた Step だけです。`on.cancel` の値が真偽値でなければ
`E-PARSE`、`false` は `E-STRUCTURE` です。`on` のキー同士の組み合わせは検査しません。

自然文の内容で規則を分ける書き方（`on: {text: true, contains: ...}` など）は書けません（PACK-41、D-43）。判定語は語彙に足さない決定で、`text` の Step が判定するのは空でないことと文字数だけです。`text` を含む `on`、または `text` の Step の規則の `on` に、規則の `on` の語彙（`command`・`args`・`missing`・`option`・`approval`・`target`・`ui`・`text`・`cancel`）にないキーがあるか、`on.text` が真偽値でないか、`on` が mapping でない（`text` の Step）と、`validate` も `compile` も `E-PARSE` にします。黙って通すと、内容を見ない規則（当たらない規則・常に当たる規則）になるためです。分けたいときは、Step を分ける、入力方式を `choice` にする、受け付けた後の確認で人が判断する、のいずれかにします。限界は `docs/known-gaps.md` の H-2 です。

## 確認（`confirm`）

入力を持つ Step は、受け付けただけでは達成にならず、受講者の確認の操作で初めて達成になります（PACK-13、R-22）。
確認を省けるのは、理由を添えて `kind: none` と明示した Step だけです。入力を持つ Step が確認も理由つきの省略も持たない場合は
`E-NO-CONFIRM` で拒否します（`wait` の Step も入力を持つ Step です）。`use` を持つ Step は入力を持たないため、確認の検査の対象外です（`input` との同時指定は `E-STRUCTURE`）。
モジュールの `confirm` が `${名前}` を含む場合は、引数で置き換えた後の宣言を検査します（`reason: "${why}"` に空文字を渡すと `E-NO-CONFIRM`）。

| `kind` | 欄 | 意味の制約 |
|---|---|---|
| `point_at` | `targets`（各要素は `view`・`path`）、`on_miss`（任意） | `targets` は 1 件以上で、どれも空でない |
| `answer` | `options`（各要素は `id`・`correct`・`label`、任意で `on_wrong`）、`on_wrong` | 1 件以上で、`id` は空でなく重複しない。`correct: true` が 1 件以上。`on_wrong` は空でない。`label` は必須で空白だけにできない（欠けは `validate` が `E-STRUCTURE` にする）。選択肢の `on_wrong` は書くなら空でなく、`correct: true` の選択肢に書けない |
| `approve` | なし | 欄を足すと `E-PARSE` |
| `none` | `reason` | `reason` が前後の空白を除いて空でないこと。無い・空・空白だけは `E-NO-CONFIRM` |

- 未知の欄・未知の `kind`・欄の欠け・型の違いは `E-PARSE`、意味の制約の違反は `E-STRUCTURE` です
- `none` の理由の欠けを `E-PARSE` でなく `E-NO-CONFIRM` にするのは、PACK-13 の「理由つき」の違反として扱うためです（2026-10-15 の決定）
- 終端でない入力の無い Step（`use` も無い）に `confirm` を書くと `E-STRUCTURE` です。確認は入力の受付の後に届くため、この形の確認は永久に届きません（PACK-35・PACK-19、D-69、2026-10-21）。終端の Step（`final: true`）の `confirm` は、形だけを検査します
- `answer` の選択肢の `on_wrong`（EP-6）は、その選択肢を選んだ誤答に返す文面です。選択肢が持たなければ Step の `on_wrong` を返します。正答の選択肢に書くと `E-STRUCTURE`、書くなら空白だけにはできません（2026-10-15 の決定。契約の版を 3 に上げました）
- `answer` の選択肢の `label`（v1.3）は表示名です。画面の選択肢と、操作のログの「選択: …」に同じ表示名が出ます。必須です。`label` の無い（欄が無い・`null`）選択肢は、`validate` が `E-STRUCTURE` で止めます（2026-10-21 の D-67。PACK-37）。`compile` は検査しないため、`label` の無いまま `compile` だけを通すと IR では ID のまま出ます。教材の CI では `validate` も流してください。前後の空白を除いて空になる `label` も `E-STRUCTURE` で拒否します（2026-10-15 の決定。契約の版を 2 に上げました）
- `label` は語彙 1.3 の語です。`pack.vocab` を宣言する教材が `answer` を使うなら、1.3 以上を宣言するか、宣言を省略してください。1.3 より前を宣言すると、`label` を書かなければ `E-STRUCTURE`、書けば `E-VOCAB-MISMATCH` になり、どちらでも通りません
- 履歴に残る値は選択肢の ID で、表示名ではありません。`label` を後で直しても、記録した履歴の再生は変わりません
- 確認の `options[].label` は、入力方式 `choice` の `options[].label`（必須）とは別の欄です。表示名の解決は 1 つの Step の確認の選択肢の中だけで行い、入力方式 `choice` の `label` へは落ちません
- `on_miss`・`on_wrong`（Step・選択肢とも）の参照先が `rejections` に無ければ `validate` が `E-REF-REJECTION` にします。`targets[].view` は `E-REF-VIEW` です

## 複数の対象を 1 つずつ分類する確認（Step を分ける）

1 つの確認で複数の対象（例: 3 枚の指摘カード）を分類させ、対象ごとの正誤を取る語はありません。`answer` に複数の問いを持たせる語は足さないことが D-69（2026-10-21）で決まっています（PACK-33）。対象ごとに Step を分けて書きます。

- 対象ごとに Step を 1 つ置き（例: `card-a`・`card-b`・`card-c`）、各 Step の `answer` で 1 つの対象だけを問います。Step は `next` でつなぎます
- 各 Step には、次の 3 つが要ります。どれかが欠けると、その対象の確認に進めません
    - 入力方式 `choice`（選択肢の `id` と `label`）
    - 選択肢ごとの受付の規則（`rules[].on.option` と `outcome: {kind: accept}`）。規則に一致しない選択は `not_in_this_step` で拒否され、確認の段に進みません
    - `answer` の確認（`options` の `correct` と `on_wrong`）
- 1 枚ごとの正誤は、Step ごとの確認の結果（最初の回答の正誤）として別々に残ります。各 Step に `lo` を書くと、学習目標の記録の対象になります
- 新しい語彙の版の宣言は要りません。`pack.vocab: '1.0'` のままで `validate` が通ります
- 学習目標の数え方（L4 など）は本節で扱いません（spec の TASK-3）

## 承認の差し戻しと再承認（Step を分ける）

1 つの Step の `approval` で「承認 → 差し戻し → 再承認」を表す語はありません。足さないことは D-69（2026-10-21）で決まっています（PACK-32）。入力方式 `approval` は欄を持たず、欄を足すと `E-PARSE` です。

書き方は、差し戻しの Step と、直した結果を承認する再承認の Step を分けることです。

- 差し戻しの Step: `on: {approval: revise}` を受付にし、承認・却下は次の行動つきの拒否にします。案の状態などの状態変化は、受付の規則の `outcome.effects` に書きます
- 再承認の Step: `on: {approval: approve}` を受付にし、もう一度の差し戻し・却下は拒否にします
- 差し戻しの後の遷移（差し戻しの Step から再承認の Step へ）は、作者が `next` に書きます
- 確認は、受け付けたこと自体が意思表示になるなら、どちらの Step も `confirm: {kind: none, reason: …}` で書けます。別に確かめたいものがあるなら `point_at` などを使います

```yaml
steps:
  - id: st-revise
    next: [{to: st-reapprove}]
    input: {kind: approval}
    rules:
      - id: r-revise
        on: {approval: revise}
        outcome:
          kind: accept
          effects:
            - replace: {path: plan/draft, attrs: {state: 差し戻し}}
      - id: r-approve-early
        on: {approval: approve}
        outcome: {kind: reject, rejection: rj-revise-first}
    confirm: {kind: none, reason: 差し戻すこと自体が意思表示のため、別の確認を置かない。}
  - id: st-reapprove
    input: {kind: approval}
    rules:
      - id: r-approve-fixed
        on: {approval: approve}
        outcome:
          kind: accept
          effects:
            - replace: {path: plan/draft, attrs: {state: 承認済み}}
```

- 現在のエンジンは `next` の `when` を実行時に評価せず、`when` の無い最初の辺だけをたどります。承認と差し戻しで行き先を分ける書き方はできないため、Step を一直線に並べます
- 遷移先の `on_enter` の効果は、現在のエンジンがまだ適用しません（TASK-242）。状態変化は、規則の `outcome.effects` に前の状態に依らない形（`replace`）で書きます
- 分けて書いた教材は、新しい語彙の版を宣言しなくても `validate` を通ります。`pack.vocab` は、使った語に合わせて書きます
- この形が画面で進むことは、試験用の教材で確かめました（2026-10-23。TERM-29）。差し戻しの後に再承認の Step へ移り、再承認の Step は候補の宣言がなくても「はい」「いいえ」「直す」の 3 件を出し、「はい」で進み、「直す」と「いいえ」は拒否になります。ST-4.1・ST-6.1 の再承認は TASK-672 で確かめます
- 「直す」の誤った対象の候補と表示名は、`input.revise` で宣言します（次の節。PACK-42）

## 承認の「直す」の候補と表示名（`input.revise`）

承認の Step で「直す」の対象を選ばせるとき、規則（`on: { approval: revise, target: X }`）に書いた対象だけをボタンにすると、
正しい対象のボタンだけが並んで答えが見え、ボタンの文言も対象の ID のままになります。これを避けるため、承認の `input` に、
正しい対象と誤った候補を並べる順に宣言し、表示名を付けられます（PACK-42・D-69。語彙 1.5。拡張点の番号は持ちません）。

```yaml
input:
  kind: approval
  revise:
    candidates:
      - {id: expect, label: 期待する結果}
      - {id: reason, label: 理由}
      - {id: scope}      # 誤った候補（規則に無い）
rules:
  - id: r-revise-expect
    on: {approval: revise, target: expect}
    outcome: {kind: accept}
```

- `candidates` は 1 件以上で、各要素は `id`（必須）と `label`（省略可）です。未知の欄・型の違いは `E-PARSE`、空の一覧・空白だけの `id`・`id` の重複・空白だけの `label` は `E-STRUCTURE` です。`label` の型は確認の選択肢の `label`（`confirm.options[].label`）と同じで、省略すると ID を表示します
- どの候補が正しいかは宣言しません。対象つきの「直す」の規則（`on.target`）を持つ ID が正しい対象で、それ以外の候補が誤った候補です。正誤の正は規則に 1 か所だけ置きます
- `revise` を宣言した Step では、規則の `target` がすべて候補に入っていないと `E-STRUCTURE` です。正しい対象が候補から漏れて、画面と判定が食い違うのを防ぎます。診断に候補・対象の値は写しません
- 誤った候補を 1 件以上入れてください。入れないと、選ぶ余地がなく、答えが見えてしまいます（強制はしません）
- モジュールの Step で `${...}` を使った宣言は、置換前の値では突き合わせず、展開後の値を `compile` が検査します
- `revise` を書く教材は、`pack.vocab` に `1.5` 以上を宣言してください。宣言が古いと `validate` が `E-VOCAB-MISMATCH` を報告します
- 画面（TERM-28。2026-10-23 時点で結線済み）は、候補を宣言順に「直す（対象: 表示名）」のボタンとして出します。`label` を省いた候補は ID が文字になります。ID は入力の宛先としてだけ使い、見える文字には出しません。どの候補が正しいかを示す表示は出しません
- 判定（JUDGE-11。2026-10-22 時点）は次のとおりです
  - 正しい対象の「直す」は、対象つきの規則に従います
  - 誤った候補の「直す」は、対象つきの規則に一致が無いとき、対象なしの「直す」の規則のうち拒否だけを上から採ります。誤った対象向けの文面は、この拒否の規則（`on: {approval: revise}`・`outcome: {kind: reject, rejection: …}`）に書きます。受付と問い返しの規則は飛ばすので、誤った候補は受付になりません。拒否の規則が無ければ、`not_in_this_step` の分類による拒否です
  - 候補にも規則の対象にも無い対象は、拒否の規則を当てず、`not_in_this_step` の分類による拒否です
  - `revise` を宣言した Step の対象なしの「直す」は、対象つきの規則が無くても拒否の規則だけを採ります
  - `revise` を宣言しない Step（語彙 v1.4 以前の形）は、従来の判定のままです

## 保存・書き出しを入力とする Step（`env_action`）

「途中の状態を保存する」「履歴を書き出す」のように、実行環境の操作そのものを Step の入力にできます（PACK-34・D-69。語彙 1.5。拡張点の番号は持ちません）。操作が成功したら受付になります。受講者の入力を教材へ差し込む語ではありません（D-50）。

```yaml
- id: st-save
  title: 途中の状態を保存する
  body: save.md
  next: [{to: st-export}]
  input: {kind: env_action, action: save}
  confirm: {kind: none, reason: 保存の操作が成功したこと自体が達成の根拠のため、別の確認を置かない。}
```

- `action` は `save`（チェックポイントの保存）か `export`（履歴の書き出し）のどちらかです。未知の値・欄の欠け・未知の欄は `E-PARSE`、`processing` を持つ Step は `E-STRUCTURE` です（保存による受付には処理中を始める経路が無く、先へ進めなくなるため）。診断に宣言の値は写しません
- 受付と達成は別です。`confirm: { kind: none, reason }` と組むと、保存の成功と同時に達成になり、効果（`on_achieved`）と遷移が続きます。それ以外の `confirm` では受付済みで止まり、確認の操作を待ちます。規則（`rules`）は照合しないため、状態変化は `on_achieved` に書きます
- 保存の Step が受付になるのは、保存が成功し、その Step が入力待ちで処理中でないときだけです。保存に失敗したときは受付になりません。受講者のコマンド・選択などの入力は、この Step を受付にしません
- `env_action` を書く教材は、`pack.vocab` に `1.5` 以上を宣言してください。宣言が古いと `validate` が `E-VOCAB-MISMATCH` を報告します
- `action: export` は宣言して `validate` を通せますが、2026-10-21 時点では実行時に達成になる経路がありません。この Step を置いた教材は、そこで先へ進めません。限界と回避は `docs/known-gaps.md` の PACK-34 です

## 処理中の進行（`processing`）

`processing` の要素に書ける欄は、`name`（空でない文字列）と `effects`（効果の列）だけです。未知の欄は `E-PARSE`、空の名前は
`E-STRUCTURE` で拒否します。

**進行の間隔は宣言できません。** `processing` の要素にも、Step にも、`pack:` にも、間隔の欄はありません。書くと `E-PARSE`
になります（PACK-44、D-43）。間隔はエンジンのビルド時の定数（web crate の `tick_interval`）で、300ms です（D-47、EVT-18）。配信する設定では、教材からも URL からも
変えられません。早送りの扱いはこの節の範囲外で、早送りの項目に任せます。

処理中に受講者が Esc を押せる長さが要る Step は、進行の件数を増やして長さを稼いでください。長さはおおよそ「件数 × 300ms」で、
20 件ならおよそ 6 秒です（ST-1.5 の規模）。効果を持たない進行（`name` だけ）を足して構いません。

```yaml
processing:
  - {name: scan, effects: [{set_flag: scanning}]}
  - {name: wait-1}
  - {name: wait-2}
  - {name: wait-3}
```

処理中の Esc は、間隔や件数によらず常にエンジンの停止です（D-22）。人が実際に押せる長さかどうかの画面での確認は
TERM-34 の担当で、2026-10-15 時点では済んでいません。

**動きの抑制（`reduce`）の受講者には、段階の表示が出ず結果だけが出ます。** 受講者の OS が `prefers-reduced-motion: reduce` のとき、
処理中の段階の行は出ないため、処理中に段階を見て Esc で止める体験（ST-1.5。LO-3）は、その受講者にはできません。動きの設定の欄は
教材の側にありません（`pack` にも Step にも書けず、書くと `E-PARSE`。A11Y-12・D-82）。エンジンも `reduce` 専用の案内は出しません。

- 処理中に止める体験を前提にした Step だけで、LO-3 の確認を済ませないでください。
- 補う場面は、チェックポイントへの復帰・承認画面での差し戻し・再実行です。補いは Step の題・`do`・本文に、教材の文面として書きます。
- 補いの文面の形（INTRO-20 の案）は、仕様の TASK-607 で決まります。ここには文面の例を載せません。
- `reduce` でも、Step の題・`do`・本文と、復帰・差し戻し→再承認の結果は、動きを抑えない場合と同じに出ます（`docs/testing.md` 5.310）。

## 拒否の分類（`category`・`defaults`・`on_reject`）

拒否の分類は 8 語（`unknown_command`・`wrong_order`・`missing_arg`・`bad_arg_shape`・`busy`・`not_in_this_step`・`not_supported`・`free_text_unjudged`）で、
型の正は contract の `judgment` です（PACK-11）。次の 3 か所の分類の語は、この 8 語で読めなければ `E-PARSE` で拒否します。

- `workshop.*` の `rejections.<id>.category`（欠け・文字列でない・語彙にない語）
- `workshop.*` の `defaults` のキー
- 章・モジュールの Step の `on_reject` のキー

- 大文字小文字や前後の空白の揺れは受けません
- `free_text_unjudged` は受付に付く語で、3 か所とも書けます
- 診断には、識別子として安全な語だけを写し、値そのものは写しません
- `defaults` が 8 分類を網羅すること、キーと参照先の文面の `category` の一致は、この検査では見ません。診断コードの条件に無いためです。`next_action` の空と差し込みの枠は、次の節の検査が見ます（2026-10-15）

## 差し込みの枠（`{{...}}`）と次の行動

拒否・問い返しの文面には、受講者が次にすべきこと（次の行動）が必ず要ります（R-21、PACK-12）。次の行動を書く欄は、拒否（`rejections`）では
`next_action`、問い返し（`clarifications`）では `how_to_answer` です。文面の `message` と次の行動の欄には、値を差し込む枠を書けます（語彙 v1.1 の EP-7、PACK-16）。

枠は `{{名前}}` か `{{名前|代替の文}}` の形です。名前は次の 6 語に限られ、式・スクリプト・入れ子は書けません。

| 名前 | 差し込む値 | 空になりうるか | 使える文面 |
|---|---|---|---|
| `input_head` | 受講者の入力の先頭の語 | なりうる（代替の文が要る） | すべて |
| `nearest_command` | 近いコマンド | なりうる（代替の文が要る） | 分類が `unknown_command` の拒否だけ |
| `step_title` | 今の Step の `title` | ならない | すべて |
| `step_do` | 今の Step の `do`（案内レベルごとの `do_levels` があればその水準の文） | ならない（Step に `do` が要る） | すべて |
| `remaining` | 処理中の残りの回数 | ならない | 分類が `busy` の拒否だけ |
| `total` | 処理中の全体の回数 | ならない | 分類が `busy` の拒否だけ |

- 分類が限られた枠は、分類を持たない問い返しの文面では使えません
- 代替の文は、値が無い（または空白だけの）ときに使われます。空になりうる枠に代替の文が無い、または空白だけの場合は拒否します
- 差し込んだ値の中の `{{...}}` は展開されません。受講者の入力に枠の形が混ざっても、そのまま文字として表示されます
- 枠を含む値は、YAML で必ず引用符で囲みます。flow 形式（`{...}`）の中の引用符なしの `{{` と、block 形式で値が `{{` で始まる引用符なしの値は、`E-PARSE` になります（AUTHOR-13。診断は行と桁だけで、値を写しません）。値の途中にある `{{` は block 形式では通りますが、書き方の保証ではないので引用符で囲んでください。4 つの場合の表と根拠の試験は `docs/schema-format-b.md` の 9 節にあります

| 診断 | 条件 | ファイル・項目 |
|---|---|---|
| `E-SLOT-SYNTAX` | `{{` が閉じていない・名前が空・枠が入れ子になっている | `workshop.*`・`rejection:<id>` または `clarification:<id>` |
| `E-SLOT-UNKNOWN` | 名前が 6 語にない | 同上 |
| `E-SLOT-CONTEXT` | その分類の文面では使えない枠 | 同上 |
| `E-SLOT-NO-FALLBACK` | 空になりうる枠に代替の文が無い | 同上 |
| `E-SLOT-NEEDS-DO` | `step_do` を使う文面が出うる Step に `do` が無い（空白だけを含む） | その Step を定義した章・モジュールのファイル・`step:<id>` |
| `E-EMPTY-NEXT-ACTION` | 次の行動の欄が空、または空になりうる枠を値なしで差し込むと空になる | `workshop.*`・`rejection:<id>` または `clarification:<id>` |

- `step_do` の検査で「出うる文面」は、Step の `on_reject`、入力を持つ Step では `on_reject` に無い分類の `defaults`、規則の `reject`・`clarify`、確認の `on_wrong`・`on_miss`・選択肢の `on_wrong` が指す文面です
- 欄が無い・文字列でない場合は `E-PARSE` です。診断には、本文・代替の文の値を写しません
- `validate` と `compile` の両方がこの検査を行います。枠に誤りのある教材は IR を出しません
- モジュールの引数の展開の後で `do` が空になる場合は、静的には見えません。展開後の IR を総なめにする `slot_check::tally_empty_next_actions` が数えます。`fandhe-pack test` への結線は TASK-404 の担当です。実行時の値の組み立てと差し込みは core の `text_fill`（TASK-274）が持ち、2026-10-16 時点では、結合試験（文面の確認 38 件と、差し込みの後で次の行動が空の拒否が 0 件であることの確認）までです

### 実行時の値の規則

- `input_head` と `nearest_command` には、教材の接頭辞（`profile.command_prefix`）が付きます。`/` を決め打ちにしません
- `input_head` は、コマンドとして読めた入力だけに値があります。自然文・選択・画面操作・承認・取り消しでは値なしになり、代替の文が使われます
- `nearest_command` は、分類が `unknown_command` のときだけ計算します。コマンド表から、編集距離（隣り合う 2 文字の入れ替えを 1 と数えます）が 2 以下で最小のものを選び、`unsupported` は選びません。同じ距離なら名前の辞書順の先頭です
- `step_do` は現在の案内レベルの `do`（`do_levels` を C → B → A の順に探します）を使い、無いときに題名で代えません。`remaining` は残りの回数、`total` は全体の回数です

## 教材テストの `cmd:`・`text:` と接頭辞

`cmd:`・`text:` の値は、入力欄に打つ文字列として画面の送信と同じ関数で分けられます（AUTHOR-7）。`cmd:` は接頭辞を含めて書きます。接頭辞が `/` 以外の教材では、鍵と分けが食い違う入力（接頭辞で始まらない `cmd:`、接頭辞で始まる `text:`、接頭辞が空のときの `text:`）を `fandhe-pack test` が `E-PLAY-INPUT-CLASS` で報告します。入力は画面と同じ判定で流し、診断があれば終了コードは 1 です。接頭辞が `/` のときは検査しません。

`fandhe-pack test` は画面の実際の表示（ビューの行・本文の表示・外観・入力欄が隠れること・見た目）と停止（Esc）を確かめません。これらは自動ブラウザの試験で確認してください。

## 教材テストの誤入力の期待（`expect`）

教材テストの `error_inputs[].input.expect` は、誤入力に対する判定の結果を書く欄です（PACK-11）。書き方は 3 つの結果（4 通りの書き方）に分かれます。

| 書き方 | 意味 |
|---|---|
| `accepted` | 受付 |
| `accepted:free_text_unjudged` | 自然文の受付（内容は判定しない注記が付く） |
| `rejected:<分類>` | 拒否。分類は `unknown_command`・`wrong_order`・`missing_arg`・`bad_arg_shape`・`busy`・`not_in_this_step`・`not_supported` の 7 語 |
| `clarified` | 問い返し |

- `rejected` は分類が必須です。分類を省くと別の拒否でも通ってしまい、誤入力の分類を確かめるという目的が果たせないためです
- `rejected:free_text_unjudged` は書けません。`free_text_unjudged` は受付に付く分類で、拒否ではありません
- `accepted` に付けられる分類は `free_text_unjudged` だけで、`clarified` には分類を付けません
- `confirmed`・`progressed`・`ignored` は語彙ではないため書けません。大文字小文字や前後の空白の揺れも受けません
- 読めない `expect` は `E-PARSE` で拒否します。診断には `expect` の値を写しません
- 読むのは `error_inputs[].input.expect` だけです。`pre[].expect`・`playthroughs` の期待は `fandhe-pack test`（TASK-404）が読みます
- エンジンで実際に判定して期待と比べる実行は、入力の判定の実装（TASK-267）と TASK-404 の後になります（2026-10-15 時点）。いまの試験は、期待の読み取りと、拒否の文面・次の行動が空でないことの静的な確認までです

## 外観（`appearance`）

`pack.appearance.theme` で画面の外観を選べます（PACK-21）。値は次の 4 つに限られ、省略すると `standard` です。

| `theme` | 意味 |
|---|---|
| `standard` | 標準（既定） |
| `mono` | 色に頼らないモノクロ |
| `high_contrast` | 文字と背景の差を大きくする |
| `reading` | 読みやすさ重視（仕様は文字 18px 以上・行間 1.7 倍以上を定める） |

```yaml
pack:
  appearance: { theme: reading }
```

- 外観は見た目だけを変えます。入力の判定・状態変化・遷移・履歴には影響しません
- 名前にない値（`dark` など）や、`theme` 以外の欄は `E-PARSE` になります。色・フォント・CSS を指定する欄はありません
- 診断には書いた値を写しません
- 外観は `main` 要素の `data-theme` で表し、どの外観でも変化の印は残ります。外観の定義の全体（契約・2026-10-20 時点の実装の状態・「Claude Code 風の外観」の読み方）は `docs/operation-profile.md` の 2 節にあります。外観ごとの見た目は、2026-10-20 時点では画面にまだ反映されません

## 左エリア（`left_pane`）

`pack.left_pane` で、左エリアに出す情報を絞れます（PACK-22）。2 項目とも省略でき、省略すると既定になります。

画面にも効きます（2026-10-25 時点）。ただし `world_list: hidden` は、種類ごとの描画部品が画面へ結線されるまで、指せる行と文書の本文も消します（`docs/known-gaps.md` の PACK-22）。

| 項目 | 値 | 意味 |
|---|---|---|
| `world_list` | `shown`（既定） | 世界の一覧を出す |
| | `hidden` | 世界の一覧を出さない |
| `view_tabs` | `all`（既定） | すべてのビューの切り替えを出す |
| | `declared` | Step が宣言したビューだけに絞る |
| | `hidden` | 切り替えを出さず、Step ごとに 1 つのビューだけを見せる |

```yaml
pack:
  left_pane: { world_list: hidden, view_tabs: declared }
```

名前にない値（`view_tabs: x` など）、文字列でない値、2 項目以外の欄は `E-PARSE` になります。このとき `E-LEFT-*` は検査しません。

設定を既定（`shown`・`all`）から変えたときだけ、設定と矛盾する Step を次の診断で知らせます。報告先は、その Step を定義した章・モジュールのファイルと項目 `step:<Step ID>` です。

| コード | 検査する設定 | 報告する場合 |
|---|---|---|
| `E-LEFT-MULTI-VIEW` | `view_tabs: hidden` | Step の `views` に 2 つ以上のビューを宣言している |
| `E-LEFT-TARGET-VIEW` | `view_tabs` が `all` 以外 | 操作の宛先（`input` の `ui_action`・`confirm` の `point_at` の `targets`、`rules[].on.ui`）のビューが、その Step の画面に出ない |
| `E-LEFT-TARGET-ROW` | 設定が既定でない（`world_list` だけの変更を含む） | 宛先の `path` が、教材のどの `put`・`replace` の `path` にも現れない |

- 画面に出るビューは、`views` で宣言した順に、種類（`kind`）ごとの最初の 1 つです。`hidden` では先頭の 1 つだけです。`views` を宣言しない Step では、ビューの ID の辞書順で最初の 1 つとして扱います（試作の仮置きで、決まった規則は後続のタスクで定めます）
- `E-LEFT-TARGET-ROW` は必要条件だけを調べる静的な近似です。経路がどこかで世界状態に置かれることしか確かめないため、画面でしか分からない矛盾は報告されません。宛先の経路は、`put`・`replace` で世界状態に置いてください。`put` の `path` に含めた `${...}` は、空文字列を含む任意の文字列として照合します
- 宛先の `view` や `path` に `${` を含む場合（モジュールの引数）は、展開前に決まらないため判定しません。`workshop.views` に無いビューは `E-REF-VIEW` が報告します
- 同じ宛先が複数あれば、同じ診断が重ねて出ます
- 診断の文面は固定です。ビューの ID や経路は、英数字・`_`・`.`・`-` だけで書かれているときに限って写します

## 文書のビューの本文（`views.<ID>.body`）

文書のビューが、練習データ（`fixtures/` のファイル）の本文を出すかどうかを、ビューごとに宣言できます（PACK-38・D-50・D-51。語彙 1.4、拡張点 EP-13）。

| 値 | 意味 |
|---|---|
| `hidden`（既定） | 題・属性・注記だけを出す（今までと同じ） |
| `shown` | 行の要素が持つ練習データの本文を、その行の本文として出す |

```yaml
views:
  v-doc: { kind: document, body: shown }
```

- 出す本文は、世界状態の要素の `fixture`（練習データの ID）で決まります。状態変化の `put`・`replace` で `fixture` を別の練習データの ID に替えると、出る本文も替わります。書き換えた後の本文は、あらかじめ別の練習データとして用意してください。新しい語は要りません
- `body` は `kind` を問わず読み、検査します。文書のビュー以外に書いても、画面は使いません
- 値は `shown`・`hidden` だけです。名前にない値（大文字を含む）と、文字列でない値（`null` を含む）は `E-PARSE`（項目 `view:<ID>`）になり、`compile` は IR を出しません。診断の文面は固定で、書いた値を写しません
- `body` を書く教材は、`pack.vocab` に `1.4` 以上を宣言してください。宣言が古いと `validate` が `E-VOCAB-MISMATCH` を報告します
- IR の型は変わりません。`body` を書かない教材の IR は、今までとバイト単位で同じです。本文の木は、版 2 の `fixture_docs` に宣言したすべての練習データが既に載っています
- 画面への表示は結線済みです（ART-18。2026-10-24）。文書のビューを選んでいるとき、世界状態の要素の `fixture` が指す練習データの本文が、その要素の行の中に出ます。要素は受付の規則の効果（`put`・`replace`）で置いてください。開始点の `on_enter` は、今の起動では適用されません
- 練習データの中の、選んだ値の差し込みは、この語では扱いません。足さないと決まっています（次の節）

## 選んだ値の差し込み（限界と回避）

受講者が選んだ値を、文中・経路・属性に差し込む語はありません。語を足さないことは D-50（2026-10-12）で決まっています（PACK-39）。

- 状態変化の経路と値は、書いた文字列そのものになります。`${名前}` は学習モジュールの引数をコンパイル時に置き換えるだけで、章の中では文字のまま残ります
- 受講者の入力の値は規則の照合にだけ使われ、世界状態には入りません。差し込みらしい欄（`value_from` など）を足しても動きません。`on_enter` などの状態変化では未知の欄として `E-PARSE` になります。`rules[].outcome.effects` では読み込みを通過し、実行時に警告（`Event::Warning`）となって入力が拒否されます
- 回避は、起こりうる入力を規則として列挙し、それぞれに固定の効果を書くことです。列挙にない値は `not_in_this_step` で拒否され、世界状態は変わりません
- 選択ごとに、属性へ固定の文面を書いて変化を見せる回避も使えます。本文を出す語（前の節）が入った後も、選んだ値を本文に差し込むことはできません。書き換えた本文は、別の練習データへの `replace` で表します
- 限界の詳しい内容と書き方の例は `docs/known-gaps.md` にあります

## 存在しない要素への `remove`・`set_attr`（`E-REF-ELEMENT`）

世界状態は空で始まり、要素を作るのは `put`・`replace` だけです。置かれていない経路への `remove`・`set_attr` は、
実行時に警告（`Event::Warning`）になり、教材テストが失敗します。`validate` は、その手前で次のように報告します
（PACK-30・D-43。診断コード一覧の版 2）。

- 教材のどこの `put`・`replace` も置かない経路を `remove`・`set_attr` が指すと、`E-REF-ELEMENT` です。
  `compile` は報告しません（`validate` だけの検査です）
- 「置く」に数えるのは、章・モジュールの全 Step の `on_enter`・`on_achieved`・`processing[].effects`・
  `rules[].outcome.effects` と、`starts[].effects` の `put`・`replace` です。`when` つきの `put` も数えます
- `put` の経路に `${...}` があれば、空文字列を含む任意の文字列として照合します
- モジュールの引数を含む `remove`・`set_attr` の経路は、引数を置き換えた後の Step で判定します。診断は Step を
  定義したモジュールのファイルに付きます
- `replace` は報告しません（要素が無ければ置くため）
- 診断は `on_enter[0]: remove target path ... is not placed by any put or replace` の形です。経路は、英数字・
  `_`・`.`・`-` だけで書かれているときに限って写します。属性の値は写しません

必要条件だけを調べる近似です。次は報告しないので、教材テストの模範解答と、実行時の警告で補ってください。

- 順序に依る不在: `put` より前の `remove`、同じ経路への 2 度目の `remove`
- `put` が通らない枝（条件・入力の違い）で置かれる要素への `set_attr`

## `pack.vocab` の書き方

`pack.vocab` は必ず書きます（VER-11）。省略すると、履歴には `1.0` と記録され、`validate` の一致の検査も働きません（PACK-31）。

- 値は、使っている語の中で最も新しい語彙の版以上を、`主.副` で書きます（例: `"1.6"`）。YAML では引用符で囲みます
- 現在のエンジンが読める語彙の上限は 1.6 です（`docs/vocabulary/vocabulary.md` の版と拡張点の対応表）。上限を超える宣言の
  履歴は開きません（`vocab_newer`。VER-7）。`validate` は、上限を超える宣言を報告しません（2026-10-19 時点）
- 語彙 1.1 の語は、`validate` がまだ検査しません。作成者が対応表で確かめます。`fandhe-pack vocab` は EP-1〜EP-9 と EP-13 を Step ごとに数えます。EP-9 は、`requires` または `unmet` を持つ開始点が指す Step の行に数え
  （`use` の Step を指す開始点は数えません。片方だけの開始点は `compile` が `E-STRUCTURE` で止めるため数えません）、`label` は拡張点の番号を持たないため数えません（AUTHOR-17）
- `fandhe-pack vocab <pack-dir>` は、Step ごとの拡張点の使用と、既存の語彙の組み合わせだけで書けた Step の数を出します（AUTHOR-9。出力の形は
  `docs/cli.md` の 12 節）。EP-7 は Step の `do` だけ（`do_levels` は数えません）、EP-8 は Step の `body_levels` とヒントの `levels` だけを数え、教材パック全体の
  `guidance_levels` と開始点の `guidance` は数えません。`pack.profile`・`pack.appearance`・`pack.left_pane` は、既定から変えたときだけ末尾に出し、Step ごとの数に入れません。
  読み込みか `compile` に診断があるときは表を出しません。`pack.vocab` に何を宣言するかを確かめるときは、先に `compile` を通します
- 語彙の版を上げるだけの変更は流れを変えないため、主版ではなく副版か修正版の扱いです。語彙が古い履歴は、適用し直して一致すれば
  変換して開きます（VER-4）

宣言と使用の一致の検査は、次の節に書きます。

## `pack.vocab` の宣言と使用の一致（`E-VOCAB-MISMATCH`）

宣言より新しい語彙を使う教材は、履歴の「語彙の軸」が宣言に頼るため、版違いの履歴の理由を特定できません。
`validate` は、`pack.vocab` を書いた教材について、次のように報告します（PACK-31・VER-14・D-43。診断コード一覧の版 7）。

- 宣言より新しい版の拡張点を使うと、拡張点ごとに 1 件の `E-VOCAB-MISMATCH` です。`compile` は報告しません
  （`validate` だけの検査です）
- 対象は EP-9（`starts[].requires`・`unmet`。語彙 1.2）と、EP-10〜EP-12（`pack.profile`・`pack.appearance`・
  `pack.left_pane`。語彙 1.3）と、EP-13（`views.<ID>.body`。語彙 1.4）と、確認 `answer` の選択肢の `label`（`confirm.options[].label`。語彙 1.3）と、承認の `input.revise`（`input.revise.candidates`。語彙 1.5）と、実行環境の操作 `env_action`（語彙 1.5）と、`do_levels`（語彙 1.6）です。
  値が既定と同じでも、欄を書けば使用です。呼ばれないモジュールの開始点・Step も数えます。何か所で使っても 1 件です
- 入力方式 `choice` の `input.options[].label`（語彙 v1）は別の欄で、対象ではありません。`confirm` の側だけを見ます
- `pack.vocab` を省略した教材は検査しません。書き方の規約は別に定めます
- `pack.vocab` が文字列でない、または `主.副` の形でない（`1.2.0`・`v1.2`・`01.2` など）ときは `E-PARSE` です。
  YAML では `1.2` を引用符で囲んでください。値は診断に写しません
- 診断は `EP-9 (starts.requires) needs vocab 1.2 or later (declared 1.0)` や `confirm.options[].label needs vocab 1.3 or later (declared 1.2)` の形で、file は定義ファイル、item は `pack:vocab` です。`label` の値は写しません
- 語彙 1.1 の拡張点は、まだ検査しません

## 本文の行の途中の改行

本文（Markdown）を 1 段落 1 行で書く必要はありません（PACK-27・D-51）。

- 前後がともに日本語（かな・漢字・全角記号）の行末の改行は、連結されます。文の途中に空白は入りません
- 英数字が接する改行（`hello` と `world` など）や、日本語と英数字の間の改行は残り、画面では空白として描かれます
- コード・強調・リンクの直前や直後の改行は、連結されません
- 段落を分けるには空行を、強制改行には行末の空白 2 つか `\` を使います

## `validate` の出力の読み方と、読み込みの失敗

`fandhe-pack validate <pack-dir>` は、診断 1 件につき 1 行（`<ファイル>: <項目>: <コード>: <メッセージ>`）を標準出力に出し、最後に最終行を 1 行出します。診断が 0 件なら終了コード 0、1 件以上なら 1 です。最終行の形は 3 つです（`docs/cli.md` 8 節）。

- `OK: 診断 0 件（形式 B(YAML)、章 N、モジュール N、Step の定義 N）`
- `NG: 診断 N 件（形式 B(YAML)、章 N、モジュール N、Step の定義 N）`
- `NG: 診断 N 件（読み込めません）`

`読み込めません` で終わったときは、構文の誤り・未知の欄・型の違い・必須欄の欠け・上限超過のどれかで、パックを読み込めていません。このとき参照の整合などの検査は流れず、読み込みの診断（`E-PARSE`・`E-LIMIT-*` など）だけが出ます。

まず、出た読み込みの診断を直してください。直すと読み込めるようになり、これまで流れなかった検査が走って、参照の欠けなどの新しい診断が出ることがあります。`OK:` で終わるまで、直して実行し直す手順を繰り返してください。最終行には教材データの文字列（ID・本文・パス）は出ません。

## 秘密情報らしい値（`E-SECRET-SHAPE`）

教材パックは public の repo に載ります。本物と紛らわしい形のトークン・鍵・接続文字列が混ざっていると、公開の前に気づけないため、`validate` は値が秘密情報らしい形に当たると `E-SECRET-SHAPE` を報告します（AUTHOR-18・D-81）。`test` の関門でも出ます。`compile` は検出しません。

- 調べる対象: 本文・練習データ・章とモジュールの Step（題・`do`・入力・規則など）・`workshop` の `commands`・`views`・`hints`・`rejections`・`clarifications`・教材テストの値
- 形: 受講中の保存の直前の警告と同じ固定の 15 形です（`docs/known-gaps.md` の SAFE-30）
- 出力: 診断はファイル・項目・形の ID だけを出し、値は写しません。同じファイル・項目・形は 1 件にまとめます
- 直し方: 明らかに架空と分かる値にします。接頭辞を崩す（例: 本物の接頭辞の代わりに `kakuu-` のような語から始める）と、形に当たらなくなります

限界です。調べるのは読み込んだ後の値だけで、YAML・TOML のコメント・map の鍵・参照されていない本文や練習データは調べません。モジュールの引数を置き換えて合成した後に初めて現れる値も調べません。社内固有の語・実在の名前との紛らわしさは `validate` の対象ではなく、公開前の確認（`docs/publish-checks.md`）が受け持ちます。【架空】の印の欠けは、次の節の `E-FICTIONAL-MARK` が報告します。

## 練習データの【架空】の印（`E-FICTIONAL-MARK`）

練習データも public の repo に載ります。本物と見分けがつかないと誤って使われるため、`validate` は練習データの見出しに【架空】の印が無いと `E-FICTIONAL-MARK` を報告します（AUTHOR-18・D-81）。`test` の関門でも出ます。`compile` は検出しません。

- 調べる対象: `workshop.fixtures` が指す、読み込めた練習データのファイル。章の本文は対象にしません
- 印の形: 1 行の中の `【架空` と、その後ろの `】`（`【架空】`・`【架空ログ】` が通ります。半角の `[架空]` は印とみなしません）
- 場所: 最初の空でない行です（Markdown なら `# 【架空】…`、テキストなら `【架空】…`）。2 行目より後ろだけにある印は通しません
- JSON の例外: 拡張子が `.json` で内容が object のときは、ルート直下の文字列値のどれか（例: `_note`）に印があればよい。入れ子の中だけの印は通しません。JSON として読めないときは先頭行の規則を当てます
- 出力: 練習データのパスごとに 1 件。診断は固定の英文で、練習データの内容を写しません
- 直し方: 見出しの行に `【架空】` を足します

限界です。印の有無だけを見て、内容が本物かどうかは判定しません。`workshop.fixtures` に宣言していないファイルは調べません。実在の private repo・社内 runner の名前との紛らわしさは `validate` の対象ではなく、公開前の確認（`docs/publish-checks.md`）が受け持ちます。試験は `crates/pack/tests/fictional_mark_validate.rs`（記録は `docs/testing.md` 5.313）です。

## `validate` が見つけない欠陥

`validate` は、次の 4 つを報告しません（PACK-30・D-43 で、検出できない限界として受け入れた範囲です）。

- 条件の充足可能性: 決して真にならない `when`（例: ある旗とその否定を `all` で並べた条件）の先の Step。静的な辺は
  あるので、到達できるものとして扱います
- Step の巡回: 無条件の `next` で前の Step に戻り、`final` に着かない巡回。モジュールの呼び出しの巡回
  （`E-MODULE-CYCLE`）だけは報告します
- 規則の遮蔽: 先の規則が後の規則を隠し、後ろの規則が決して選ばれないこと。規則は上から照合し、最初に一致した
  ものの `outcome` を使います。たとえば引数の条件を持たない `make-item` の規則の後ろに、`name` の値を指定した
  `make-item` の規則を置くと、後ろの規則は使われません。規則は具体的なものから先に書いてください
- 実体どうしの経路の重なり（MOD-18・TASK-251 の決定）: 意図した共有と誤りを経路だけでは見分けられないため、
  報告しません。書き方は「実体どうしの世界状態の経路」を見てください

補うには、教材テストの `playthroughs` に、すべての開始点と、条件で分かれるそれぞれの枝を通る模範解答を書き、
各枝が `final` まで進むことを確かめてください。経路の重なりは、2 周分の通しで各周回の成果物が残ることで確かめます。遮蔽は、模範解答と誤入力で、規則ごとに意図した結果になる入力を
通して確かめます。

## 新しい表現が要るとき（拡張点の追加）

既存の語の組み合わせで書けない表現が要るときは、教材ごとにエンジンを直さず、汎用の名前つき拡張点として足します。
教材パックからは名前の欄を書いて使うだけで、任意のコードは書けません。実行時に拡張点を登録する仕組みもありません。
手順は `docs/extension-point-procedure.md` にあります。

## IR の出力と配信物（`compile`）

`fandhe-pack compile <pack-dir> -o <file>` が書く IR は、画面に配る IR そのものです。標準出力に出す IR と `-o` のファイルは同じバイト列で、`-o` を付けたときは標準出力に何も出ません。

- 同じ内容の教材パックは、何度 compile しても、別のディレクトリへ写しても、同じバイト列の IR になります。IR にパス・時刻・乱数は入りません
- 診断が 1 件でもあるときは、ファイルを作りません。同じ名前のファイルが既にあっても書き換えません
- 書き出せないとき（親のディレクトリが無い・既存のディレクトリを指すなど）は、`error:` の 1 行を標準エラー出力に出して終了コード 2 で終わります。一時ファイルへ書いてから置き換えるので、途中まで書いた IR は残りません
- 配信物には `IR_FILE=<file> tools/build-web.sh` で入ります（`ir/main.json`）。手元の画面で確かめる手順は、次の「compile した IR を手元の画面で確かめる」にあります。公開先への配信は TASK-121 の側です
- 一部の章だけを配る試行用の IR は、`fandhe-pack compile <pack-dir> --chapters <章の id>[,<章の id>...] -o <file>` で作ります。選んだ章と、そこから呼ぶモジュールの実体だけが残り、範囲外の章の開始点は IR に入りません（PACK-43・D-67）。該当する章が無い・同じ id の章が 2 つ以上あるときは終了コード 2 です。教材パック全体の検査は絞らずに行います
- 章の `next` は同じ章の中の Step だけを指せます。他の章の Step を指すと `validate` も `compile` も `E-REF-STEP` です。章をまたぐ移動は `next` ではなく、章ごとの開始点で表します
- 外部仕様は `docs/cli.md` の 10 節（AUTHOR-8）です

## compile した IR を手元の画面で確かめる（AUTHOR-21）

compile した IR は、受講者に配る配信物の教材そのものです。手元でその配信物を開けば、受講者が見るのと同じ成果物の画面を、公開の前に確かめられます。

前提: Rust・wasm のツールチェーンと Node が要ります。版と導入は `README.md` の「前提」と `docs/toolchain.md` を見てください。Rust を入れない端末で、1 回の操作の結果だけを手元で見る形（プレビュー）は未決です（AUTHOR-22・TASK-428）。この節の手順は、その形とは別です。

手順:

1. `target/debug/fandhe-pack validate <pack-dir>` が `OK:` になるまで直します
2. `target/debug/fandhe-pack compile <pack-dir> -o <file>` で IR を作ります
3. `IR_FILE=<file> tools/build-web.sh release` で配信物を作ります。出力は既定で `dist/web` です（`OUT_DIR` で変えられます）。`TEST_HOOKS` は空のままにします。`TEST_HOOKS=1` の配信物は試験用の口を持つので、確かめにも配布にも使いません
4. `node tools/serve.mjs --dir <出力> --base /<任意の名前>/` で配ります。待ち受けは 127.0.0.1 だけで、ポートの既定は 8765、gzip は有効です。`make serve` は既定の `dist/web` と `/subpath/` で同じことをします
5. Chrome で `http://127.0.0.1:8765/<任意の名前>/` を開きます。`?ir` は付けません。誘導に従って最後まで進めます。各章の最初の Step で、「いまやること」と本文が出ます
6. 章の開始点を直接開くときは、`/<任意の名前>/?start=<開始点 ID>` とします。ID は IR の `starts` の `id` です。開くと、その章の最初の Step の題と、入ったばかり（確認待ちでも達成でもない）の状態、上部の位置（`<章の ID>　Step 1 / K`）が出ます
7. ID が `starts` と完全一致しないときは、開かずにコードだけを示します（`start_unknown`）。入れた値は画面に出ません。節の ID でも、開始点でなければ開きません（DLV-7・DLV-9・D-68）

同じ成果物であることの根拠:

- 配信物の `ir/main.json` は、compile の出力とバイト単位で同じです
- 配信物は試験用の口を持たない配信する設定です
- 受講者に配る配信物も、同じ作り方で作ります。違うのは配信元（手元の 127.0.0.1 か、公開先か）だけです。公開先への配信（`deploy.yml`）は未実装（TASK-121）です

注意:

- 保存済みの履歴はオリジンごとに分かれます。手元の確認の履歴は公開先に持ち越されません
- 同じ教材を開き直すと、続きから始まることがあります。最初から確かめるときは、新しいブラウザの文脈（シークレットウィンドウなど）で開きます

限界:

- 本文の確認は自動ブラウザによる AI の代理であり、人の作成者が画面を確かめた記録は含みません
- 試験は試験用の教材（`crates/web/tests/data/ch0_3_pack`）で行いました。本物の CH-0〜CH-3 での流し直しは未実施です
- 根拠の試験は `tools/browser/author-preview.test.mjs`（`docs/testing.md` 5.292・5.298）です

## 案内レベル（`guidance`・`body_levels`・`do_levels`・ヒントの `levels`）

案内レベルは `A`・`B`・`C` の 3 水準です（EP-8。PACK-17）。`A` が最も手厚く、`C` が最も薄い水準です。

- 水準 L で出す本文は、`C` なら `body_levels.C`、`body_levels.B`、`body` の順に探します。`B` なら `body_levels.B`、`body` の順です。`A` は `body` だけです
- 水準 A の本文は `body` に書きます。`body_levels` に `A` の鍵は書きません。書くと `validate` も `compile` も `E-STRUCTURE`（Step ごとに 1 件）で止めます
- `do` も水準ごとに書き分けられます（`do_levels`。語彙 1.6、PACK-50）。鍵は `B` と `C` だけで、水準 A の文は `do` に書きます。例: `do: "<コマンド名> を送る"` と `do_levels: {B: "アイデアを書くコマンドを送る"}`。順序違いの拒否の次の行動に `{{step_do}}` を置くと、現在の水準の文が入り、水準 B で隠すコマンド名が出ません
- 水準 L で出す `do` は、`C` なら `do_levels.C`、`do_levels.B`、`do` の順に探します。`B` なら `do_levels.B`、`do` の順です。`A` は `do` だけです。本文と同じ倒れ方です
- `do_levels` を持つ Step は `do` が必須です。値は空にできません。鍵 `A`・空の値・`do` の欠落は、`validate` も `compile` も `E-STRUCTURE` で止めます。値は文字列で、モジュールの Step では `${名前}` を置換します（置換の後に空になると `E-SLOT-NEEDS-DO` などで止まります）
- `do_levels` を書く教材は、`pack.vocab` に `1.6` 以上を宣言してください。宣言が古いと `validate` が `E-VOCAB-MISMATCH` を報告します
- ヒントは `levels` に出す水準を列で書きます。省略と空の列は全水準を意味します
- `pack.guidance`・`starts[].guidance`・`body_levels` のキー・`pack.guidance_levels` のキー・ヒントの `levels` の要素が `A`・`B`・`C` でなければ、読み込みで `E-PARSE` になります。小文字も拒否します。診断に書いた値は写しません
- `pack.guidance_levels.<水準>` は `hide_command_kinds`（`builtin`・`skill`・`flow`・`unsupported`）と `hide_words`（文字列の列）だけを持てます
- 隠す語の漏れ（`E-GUIDANCE-LEAK`）は `validate` だけが検出します。水準 B・C について、`hide_command_kinds` に当たる種類のコマンド名と `hide_words` が、その水準で出る本文または `do`（`do_levels` があればその水準の文）に含まれると報告します。対象は、`body_levels` を持つ Step の水準 B・C（本文と `do`）と、`do_levels` を持つ Step の水準 B・C（`do` だけ）と、開始点の `guidance` が B・C の章の全 Step およびその章が呼ぶモジュールの全 Step の同じ水準です。単純な部分文字列の包含で調べる近似の検査です。実体の引数で渡す `do`・`do_levels`（`${...}`）は、引数と既定値を置換した後の文字列まで調べます（PACK-52、TASK-71 3/3）。置換の前の字面にすでに語がある水準は、定義の側の 1 件にまとめます。診断に隠す語・引数の値・本文は写しません
- 次の 2 つは検査の外で、作成者の規約です（D-43。PACK-52）。ヒントの文面（段 2・3）に隠す語を書く場合は、ヒントの `levels` で B・C に出さないようにします。水準 B・C で使う章には、開始点の `guidance` か `body_levels` を宣言します。宣言の無い章の本文は、どの水準で出るかが決まらないため、検査しません
- 案内レベルは実行全体で 1 つです。モジュールの実体ごとには変えられず、章の開始点の `starts[].guidance` で渡します（PACK-45）
- ヒントが出ない水準（`E-HINT-HIDDEN`）も `validate` だけが検出します。定義のあるヒントを持つ Step で、ある水準にヒントが 1 つも出ないと、水準ごとに 1 件報告します。未定義のヒントの ID は `E-REF-HINT` の担当です

## ヒントの段（段の意味は教材側の約束）

ヒントの「3 段」は教材側の約束で、語彙にもエンジンにもありません（D-55。GUIDE-8）。ヒントを出せる数の上限は、現在の案内レベルで出せる数までです（GUIDE-17）。

- 段は Step の `hints` の並び順で数えます。ヒントの定義のうち `levels` はエンジンが読みます。画面は `text` が文字列のときだけ、開いた段の文面として出します（語彙の語としては定めておらず、文字列でなければ固定の文を出します。TASK-530）
- 推奨の約束は、1 段目が作業の場所・工程、2 段目が使う道具の名前、3 段目が完全なコマンド（または答えを含む文）です。GUIDE-8 は検討中で、教育上の適切さは人の試行で確かめていません
- 約束どおりかの構造は、教材テストから `fandhe_workshop_pack::hint_stages::check_hint_stages` で確かめられます。段数・Step ごとの例外の段数・答えの段・任意の答えの照合（宣言した欄の文字列が答えを含むか）を宣言として渡すと、食い違う Step が `uid` つきの一覧で返ります。宣言の誤りは `Err` です
- 定義の無いヒントの ID は段に数えません（未定義の参照は `E-REF-HINT` の担当）。`hints` が空の Step は確かめませんが、未定義の ID だけを持つ Step は段数 0 として報告されます
- `validate` は段の数を報告しません。`fandhe-pack test` は未実装（TASK-404）で、2026-10-23 時点の呼び出し元は試験だけです
- 中身の適切さ（場所・道具・コマンドの意味）は確かめません。答えの照合は部分文字列の包含の近似です

## 上流との対応表（Step ごとの上流の行）とヒントの括弧書き

Step ごとの上流の行を持つ欄は、語彙にありません。足さないと決めました（D-70、2026-10-22。PACK-46）。Step に `upstream` のような欄を書くと、`compile` も `validate` も `E-PARSE` で止まります。値は診断に写りません。

- 対応表は、教材パックでは読み込まれない別の文書（教材 repo 側）に置きます。鍵は章・モジュールの ID と Step の ID です
- Step の ID の一覧は `fandhe-pack vocab` の表の `scope,step` 列から取れます（`docs/cli.md` の 12 節。展開後の複製は含みません）。別の文書の行と突き合わせ、存在しない Step ID を教材テストで検出してください
- 参照版（参照元の名前・commit・版つきのリンク）は、パック全体の `refs` に書けます。型は検査せず、IR にそのまま写ります。Step とは結びつかず、上流の文面は写しません（D-11）。置き場の最終の形は教材の部品の定義（TASK-717）が決めます
- 参照元の版を上げたときに影響する Step の洗い出しには、`tools/upstream-impact.mjs`（TASK-182）を使えます。エンジン（crate）は対応表を持たず、道具は `tools/` にあります。対応表は CSV（版 1）で、必須の列は `scope,step,ref`、任意の列は `path`（上流 repo の中の相対パス。空は参照名の全体に依拠）と `lines`（人が読む欄）です。`scope,step` は `fandhe-pack vocab` の表と同じ文字列で書きます。使い方は `node tools/upstream-impact.mjs --map <表> (--changed <参照名>... | --changes <ref,path の CSV>) [--vocab <vocab の出力>]` です。出力は `scope,step` の表と `# ` で始まる集計行で、終了コードは 0（列挙できた）・1（`--vocab` に無い Step を指す行がある）・2（入力の形が不正。標準出力は空）です。行番号では照合しません。実際の対応表と Step ID の突き合わせの教材テストは教材 repo の担当です。版を上げる全体の手順（教材テスト・公開前の人の確認と記録・AI の生成物の扱い）は `docs/upstream-bump-procedure.md` にあります
- ヒントの 3 段目の日本語の括弧書き（「組み立ての例」など）は、コマンドの文字列の外（ヒントの別の文）に置きます。教材側の約束で、語彙に語は足さず（D-55 と同じ扱い）、守られているかの検査もありません

根拠の試験: `crates/pack/tests/upstream_map_gap.rs` の `pack46_`（`docs/known-gaps.md` の PACK-46）。洗い出しの道具の試験は `tools/upstream-impact.test.mjs`（`make test-upstream-impact`。`docs/testing.md` 5.235）。

## 講師資料の補助ファイル（`instructor/instructor.yaml`）

講師資料（次以降の機能）に要る値（章の所要時間・模範の例・追加の声かけなど）は、教材パックの `instructor/instructor.yaml` に置く受け口を用意しています（PACK-49）。

- 置き場は教材パックの根の `instructor/instructor.yaml` です。形式 A（TOML）の教材パックでも、名前は `.yaml` のままです
- `validate`・`compile` は読みません。置いても診断は増えず、IR と `content_hash` はバイト単位で変わりません。値は受講者向けの IR にも載りません
- 中身の欄の検査と不足の診断（`E-INSTR-*`）、講師資料の生成は次以降です。いまは構文が不正でも通ります
- `E-SECRET-SHAPE` の対象外です。秘密情報や社内固有の語を書かないでください。公開前の `make check-internal-info-secrets` は全ファイルを照合します
- `metrics` の CSV には `toml`・`yaml` の通常ファイルとして補助ファイルの行が出ます（`docs/known-gaps.md` の PACK-49）
